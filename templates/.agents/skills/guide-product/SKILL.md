# Guide product work

Read existing AGENTS.md/instructions, the current request and relevant sources/decisions. In an initialized instance, also read .kit/project.json and use output_language. When adopting an existing repository by reading this kit as a reference, keep its authoritative docs, language and tracking; missing .kit files do not imply missing product knowledge. Explain choices to people unfamiliar with product/engineering. Saved state supports resumption, but the current request can change work type.

Initialization creates a new directory; it does not migrate or merge an existing repository. For manual adoption, read the relevant procedure and models from the kit source, then record the question, baseline, criteria, findings and next action in the repository's existing responsible records. Links to models describe formats, not required output destinations. Instance configuration, catalog/materialization and work helpers apply only when those files are installed. Do not claim helper checks, native skill discovery or automated adoption when only manual reading was performed.

Read execution_mode and work scope. In guided mode, conduct the current result and recommend the next transition. In continuous mode, proceed through relevant already-authorized steps toward bounded criteria within allowed_stages/stop_after and max_rounds. Do not request routinely already-granted approval; record transitions with results/evidence. Ask about material decision-changing gaps and continue independent work. Pause with state/reason/next step for dependent answers, external authorization, limits or user request. Do not invent answers, label research as validation or persist without progress. Helpers do not open sessions or resume after the assistant ends.

Read [.kit/WORKFLOWS.md](../../../.kit/WORKFLOWS.md) for entry, artifacts and output. Do not restart discovery for every feature or judge simplicity by its name. Examine scope and uncertainty.

Choose depth by risk/missing information: clear reversible edits can use existing records; bounded changes use identified work; shared decisions belong in foundations. Do not create a PRD, architecture or all stages just to fill a process. At closure, review implicit choices and deliverable clarity according to .kit/METHODS.md.

Read [.kit/METHODS.md](../../../.kit/METHODS.md) for file authority, change version/base and completion criteria. Update artifact register/handoff when materializing deliverables.

Use [stage information](../../../.kit/STAGE_INFORMATION.md): reuse current answers/decisions and ask only about gaps changing the next action. Defer irrelevant information with a review condition; anticipate constraints invalidating the bet. Models are not a complete initial questionnaire.

Before execution, state question/outcome and sources used. Work within requested scope, using relevant available skills. Do not require founders to choose technologies without comparing consequences. Small changes do not require loading every document/skill.

Select a local procedure from [.kit/SKILLS.md](../../../.kit/SKILLS.md): research-product, assess-feasibility, design-experience, define-brand-design, plan-engineering, review-security, deliver-slice or evolve-product according to question/stage. They are included in the project, independent of personal skills. External specialists can complement them; absence does not remove the local procedure. Without automatic discovery, read and apply the indicated SKILL.md.

Review relevant [open questions](../../../docs/product/context/open-questions.md) on entry/resumption. At closure, record sourced resolution or leave open/deferred with a reason. For material claims or conflicting data, read [evidence review](../../../docs/product/reviews/evidence-review.md); save source/version/limits before using evidence for a decision.

Review assumptions for important hypothesis-based decisions, conflicting sources or requested critique. Use challenge-assumptions if available; otherwise read its local SKILL.md. Do not create reviewers/agents automatically.

When useful and authorized, delegate bounded independent research/review with question, recoverable sources/base, relevant skill, output, write scope, stopping condition and integration owner. A skill is a procedure; a subagent is separate execution and can consume additional time/usage. Prefer readers and one writer per shared source; use explicit work IDs and isolate overlapping edits. Do not spawn a role per stage, equate synthetic personas with user research, or accept generated review as authority without checking evidence. Read host compatibility/limits in .kit/SKILLS.md only when relevant.

Separate proposal, founder decision and evidence. Desk research concludes with signals/limits; never simulate interviews, usability or payment as facts.

For technical recommendations/decisions, use [technical decisions and review](../../../docs/product/engineering/decisions-and-technical-review.md). Start from aligned context/explicit preferences; compare, recommend and challenge. Record final user choice separately and adapt consumers; do not claim a requirement is met when a conflict is demonstrated.

Use proportional local requirements/plan/task/verification contracts. Keep one authoritative source per slice, referenced by general models.

For requested local development, use [structure and local execution](../../../docs/product/engineering/structure-and-development.md), inspect the environment and conduct work with criteria/evidence. Authorized implementation uses proportional specs/plans and available tools. Do not publish or purchase services merely to validate locally.

Close with a concrete deliverable, result, limits, updated references/effects and next decision point. Generating Markdown does not finish a phase.

Use [stage contracts](../../../.kit/STAGE_CONTRACTS.md) for inputs/outputs/resumption; ask about material blockage, not to fill every model.

## Organization and results

Read authoritative sources and any selected work relevant to this request. For a simple edit, preserve existing records; do not create work/state or load process guides just to apply the skill. Consult [organization](../../../.kit/ORGANIZATION.md) when destinations/authority need clarification, [catalog](../../../.kit/CATALOG.md) when selecting/materializing a missing artifact, and [cycles](../../../.kit/WORK_CYCLES.md) when managing work state, resumption or preserved evidence. Models guide format, not observed results; materialize only what is needed and preserve existing knowledge/proofs.

For continuity, also read docs/product/README.md and current definitions of affected capabilities. Pin recoverable bases; distinguish product capabilities, technical components and work IDs. At closure, consolidate relevant outcomes/decisions into current sources with provenance while retaining change history/proof.

For knowledge audits, consolidation, outdated documentation or capability history, select maintain-knowledge. It can enter directly from an existing product; do not repeat discovery or the implementation workflow just to repair documentation.

For human consultation, route through repository purpose/usage and docs/product/README.md before method internals. Separate intent, current product definitions and particular change outcomes. A selected completed work is historical, not an active next task. With existing docs, link authoritative sources rather than duplicating them into the default layout.

Keep agent instructions small and durable: relevant conventions, observed pitfalls and verified pointers. Route to shared responsible product sources rather than copying manuals, progress or code inventories into another AI memory. Adopt sufficient existing documentation instead of rebuilding it under the default layout. Retain decisive evidence with origin/version; disposable scratch must not be its only recoverable home. On reentry, reconcile differing document states before consuming them; distinguish proposal, implemented behavior and confirmed availability rather than choosing the newest claim automatically. After interruption, inspect relevant files/local changes and actual action results since the last checkpoint. Handoff may lag behind an interrupted write; verify before repeating a mutation, and record a reconciled next action without pretending to recover unsaved context.
