# Define experience

Read context, problem, rules and current material. Work in [flows/prototype](../../../docs/product/experience/flows-and-prototype.md). The authoritative source is identified current/proposed behavior, not an old screen assumed to be a rule. Figma/personal skills are not required.

1. Choose a journey answering the current question. Identify trigger, person, objective, objects/locations, actions, feedback and outcome. Separate provenance, organization and access for related records.
2. Compare materially different alternatives, including a simple one. Explain navigation, understanding and continuity consequences. Do not impose option counts or design every screen for a small decision.
3. Cover relevant states: empty, loading, error/retry, permission denial, lost access, undo/correction, relocation and concurrent interaction. Make predictable and recoverable effects explicit.
4. Produce a storyboard, Mermaid, sketch or local prototype according to uncertainty. State the question, what is real/simulated/omitted and the conclusions this representation permits. Label provisional decisions and synthetic data. If creating UI, inspect rendered representation, responsiveness/accessibility with available tools; exercise relevant content/width variations using the review procedure and declare what could not be rendered or checked. Do not require every combination. Diagrams do not replace usage tests.
5. Challenge hierarchy, names, signals, feedback, focus/keyboard and action effects. With real observations, record attempt, expected/observed and source; otherwise propose a protocol and keep exploratory conclusions.

Review visual and editorial defaults against the actual audience/task: identical cards for unrelated information, decorative badges/headlines, meaningless metrics, generic success/error copy, repeated punctuation patterns and motion without purpose. A familiar pattern or an em dash is not inherently wrong; retain what improves understanding. State a brief-specific rationale, use real terminology, and check loading, stale/conflicting data, failure recovery and focus after updates. Changing colors alone does not fix these issues. Prefer the existing design source and tools; do not install a design engine or duplicate product/design documents merely for an audit. References inform judgment, not a universal blacklist.

Output: flows/rules/states, recommended/selected alternative, reasons/questions, test criteria and spec/design handoff. Identify consumers in the [artifact register](../../../docs/product/context/artifact-register.md). A visual proposal is not founder approval.

For UX/UI review, apply [design/accessibility review](../../../docs/product/experience/design-and-accessibility-review.md): heuristics, applicable WCAG criteria, status/severity/evidence and verification. Depth follows material: wireframe risks/intent, rendered results, relevant code tests. Without users, do not claim validated usability.

## Organization and results

Read authoritative sources and any selected work relevant to this request. For a simple edit, preserve existing records; do not create work/state or load process guides just to apply the skill. Consult [organization](../../../.kit/ORGANIZATION.md) when destinations/authority need clarification, [catalog](../../../.kit/CATALOG.md) when selecting/materializing a missing artifact, and [cycles](../../../.kit/WORK_CYCLES.md) when managing work state, resumption or preserved evidence. Models guide format, not observed results; materialize only what is needed and preserve existing knowledge/proofs.
