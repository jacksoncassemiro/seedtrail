# Define brand and design

Use existing context/problem/flows. Read [brand](../../../docs/product/brand/brand.md) and [DESIGN.md](../../../docs/product/brand/DESIGN.md). No Figma/personal skills required. Image/design tools are optional, used only when relevant and available.

- Start with promise, audience, relevant differentiation, personality/voice and constraints. Positioning is a sourced hypothesis, not an invented market response. Preserve existing brand decisions for a component-only request.
- Explore visual direction with rationale: typography/hierarchy, colors, contrast, composition, spacing, imagery/icons and language. Compare suitability/limits instead of choosing a popular visual bundle.
- After identifying direction, record semantic tokens, component variants/states, layouts, responsiveness, interface copy and accessibility requirements in DESIGN.md. Distinguish decided, proposed and inherited choices. Do not generate unused components.
- When code exists, extract actual conventions/tokens before proposing replacement. Available extraction tools can help, but local reading remains supported; avoid a competing second source.
- For in-scope visual decisions, create a reviewable representation and inspect rendering. Exercise relevant content/width variations in used components; follow DESIGN.md for observed combinations and limits. Declare rendering limitations; written tokens do not demonstrate visual quality. Check incorporated image/font licenses.
- Where code consumes the contract, link current decisions to implementation names/locations and change references. Identify affected consumers and reviewers; check mismatches and justified exceptions. Scale shared-component maintenance to actual reuse/capacity, using the existing contract/history rather than a second visual guide or an automatic per-component log.

Output: brand/DESIGN linked to flows/specs, decisions and review criteria. Engineering consumes this contract; later changes review relevant consumers. Do not put backend architecture here or claim assistant-approved identity.

For visual/component critique, use [design/accessibility review](../../../docs/product/experience/design-and-accessibility-review.md). Reuse current flow/criteria; final brand is not needed to test a simple interaction question.
