# Maintain product knowledge

When the method or its skills change, inspect affected triggers, conflicting instructions, useful outputs, real dependencies and reader needs. Merge/remove overlap; add a skill only for distinct work not adequately guided by existing procedures. Do not install another catalog, memory store or observer merely because it is popular.

For a material skill change, define a few observable outcomes and exercise realistic positive/adjacent negative requests in isolated artifacts. When independent evaluation is useful and authorized, give the reviewer the request, skill and raw sources without the intended answer or suspected fix; inspect actual outputs/side effects. Separate format validation, explicit-use behavior and native discovery. An LLM reviewer or passing frontmatter does not certify all scenarios; record the version, cases, failures and limits in the existing review record. Use an available host skill creator/validator as a complement, not a runtime dependency. [OpenAI skill evaluations](https://developers.openai.com/blog/eval-skills) describe this approach.

Read the product map or existing responsible entry and affected sources, relevant open questions and decisions. In an initialized instance, read .kit/project.json for output_language and selected work; when using the kit as a reference in an existing repository, preserve its instructions, language and authoritative records without inventing configuration. Use [organization](../../../.kit/ORGANIZATION.md) when destinations/authority need clarification and [work contract](../../../.kit/WORK_CONTRACT.md) when managing an identified change. A small correction can update its existing source; significant consolidation has a bounded work ID and recoverable baseline.

Determine the reader and question before adding files. Keep product intent, current behavior, architecture/contracts, user guidance and historical evidence distinct. Modules/submodules are optional navigation groupings, not code boundaries or mandatory folders. Requirements/scenarios can remain together until separate ownership or difficult consultation justifies splitting. Preserve stable IDs when regrouping.

For each affected material claim, trace origin and actual state. Research needs source/date/limits; decisions need authority/reasons; implementation claims need inspected code or execution evidence for the examined version. Reconcile discrepancies instead of treating plans, old reports or generated text as the current system. For an existing implementation, inspect relevant source/contracts; do not mirror file trees, functions or inferred diagrams into documentation.

Keep one current authority per rule. Link detailed rationale/proof at the originating work/decision rather than copying it. Fix incorrect links with reasons and retain superseded decisions. If an evidence file must change, preserve an identified exact snapshot or perform/re-record relevant verification; never replace a digest to pretend old verification covered a new version. Historical evidence remains tied to its version.

For meaningful capability evolution, update short history rows beside its definition: ISO date, IDs, effect/type, base/revision, originating work and confirmed delivery version/date or unreleased. One change may affect several capabilities. Independently version capabilities only with independent distribution/contracts. Use [delivery notes](../../../docs/product/delivery/release-notes.md) when audience/version consolidation is useful; completed work is not a published release.

Check dependency result/contract/version, required versus observed availability and affected consumers. Update map and useful register entries without duplicating their entire contents. Revise relevant design, contracts, operation and user/integrator guides; if no update applies, record why in convergence. Do not publish or expose internal material merely because documentation exists.

Review links, names, states, baseline and discrepancies. Use relevant existing checks; file/hash checks do not certify semantic consistency. Keep missing verification and deferred questions explicit. Output a corrected/consolidated authoritative source or a concrete audit with findings, evidence, consumer updates and limits, plus work verification/convergence when appropriate. Do not create a second mandatory audit report if an existing one answers the question.

Make the map readable by user questions: intent, current behavior/parts, brand/UX, architecture/operations and change provenance. Use distinct content structures per discipline; a table/index does not imply identical document forms. Avoid exposing missing library models as completed knowledge. Completion now captures outside-work proof bytes; use preserve-evidence before revising legacy completed work sources, requiring matching original hashes. Do not manufacture missing historical bytes.

For feature documentation, distinguish authoritative current rules, change specs, reader-facing guidance and execution evidence. Keep the feature consultation address stable through behavior changes; work IDs are not feature identity. A justified regrouping or correction may move the authority: preserve identity/provenance, record the reason and update the map/current consumers. Retain a brief pointer at an old referenced address when useful for continuity, without repeating rules; preserve historical bytes rather than rewriting old proof links. For new projects, prefer one current features page combining rules/scenarios, usage/limits and short history when they serve the same readers. Do not require a separate manual and normative definition. Preserve useful existing authoritative sources and link separate contracts without duplicating rules. Grow by domain/subtopic when content warrants it; do not mirror frontend/backend automatically. Verify available versus proposed behavior before updating a manual.

Keep current requirements, business rules and acceptance scenarios in that authoritative definition; change specs describe deltas and relevant regressions. Expected outcomes are distinct from dated pass/fail results and proofs at the change's origin. A recorded decision can define behavior before implementation, but generated text is not approval; label decided, implemented and available states accurately. Consolidate changed rules/scenarios at closure without rewriting historical verification or adding a mandatory criterion-ID registry.

Check consultation by reader questions, including flows/data/access, technical contracts/diagrams, quality, operations and dependencies where relevant. A new reader should find current answers directly from the feature and its shared sources, not reconstruct all archived changes. Use task-based evaluations and record gaps; AI role simulation is exploratory evidence, not observed human usability. Keep temporary host plans/memory from becoming the only home of material decisions. After concurrent helper conflicts, reload/reconcile instead of overwriting; local state protection is not a distributed document transaction.
